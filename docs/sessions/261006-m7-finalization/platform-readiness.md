# M7 三平台隔离入口只读准备清单

## 这份文档是什么

本清单回答一个问题：主脑要派真实 M7 基线卡时，Linux / macOS / Windows 三平台的隔离入口、运行时、模型缓存、已授权样本与参考稿，是否**当下**可用。

本卡只做只读准备：不启动服务、不安装依赖、不下载模型、不测识别、不部署。所有读数是一次采样，带采样时间；**历史收据不是新运行时资格**。

## 采样方式与边界

- 只读探针输出白名单：平台/OS、Python 版本、隔离源码 SHA、模型缓存是否非空、样本各格式计数、参考稿存在性、候选隔离端口是否空闲。
- 不输出样本路径、媒体哈希、转写正文；主机地址、账号、路径只以「平台标签」形式出现在本地私有记录里。
- 平台标签沿用维护者运维记录中的机器布局（Mac Studio、Mac mini、Windows 计划任务主机）；远端主机可 SSH 者取本次实时读数，不可 SSH 者取本机既有隔离目录读数。
- 端口空闲是采样当时的准备线索，日后不保证；正式基线卡仍须按 `docs/guides/http-baseline.md` 重新抽取并 `ss`/等价方式确认。

### 读数说明与已知不确定项

- **Windows 模型缓存 = unknown，不是「不存在」。** 只读探针在 Windows 上用 `Get-ChildItem -Recurse` 统计模型目录字节，读数为 0；PowerShell 5.1 的递归不跟随 junction/reparse point，而模型目录很可能正是这种链接形态。一次改用 junction 探测的尝试没有返回可解析输出，因此本次**没有取得肯定或否定读数**。历史 M7 收据里该机 health 曾返回 `model=paraformer`、`worker_alive=true`，但那不构成本次运行时的资格证据。下一步是用一条能跟随 reparse point 的只读命令复核，而不是安装模型补齐。
- **Mac Studio 未找到 M7 隔离树与样本。** 本次只确认了生产 clone 存在且模型非空。M7 隔离树、样本、参考稿只在一个候选根路径上查过且未命中，没有做全盘搜索。这是准备缺口，不等于该机不存在隔离树，更不等于机器不存在。
- **macOS 隔离机 `ffmpeg` 不在非交互 PATH。** 该机非交互 shell 的 PATH 里查不到 ffmpeg；历史收据里该机做过测量，但本次不据此推断能力。派基线卡前需在该机确认解码入口，否则多格式输入的解码口径无法闭合。
- 三机的隔离源码 SHA 前缀相同（`492fe19`），是上一次 M7 收据冻结的树。**它不是本卡的正式合并 SHA**，实际测量仍等共同正式合并 SHA。

## 建议的隔离启动方式（不执行）

- Linux：按 `docs/guides/http-baseline.md` 的「Linux 隔离运行」，独立 Python 3.12 venv + `requirements-server-linux.txt`，模型目录软链到私有缓存，隔离 checkout 检出目标合并 SHA，WS/HTTP 各取一个随机高位端口并先确认未监听。
- macOS 隔离机：与 Linux 同构，依赖改用 `requirements-server-macos.txt`，隔离 checkout + 私有数据目录 + 私有结果目录（目录 `0700`、文件 `0600`）；启动前先确认该机的解码入口可用。
- Windows：沿用既有隔离准备根的布局（隔离 checkout、样本、gold、结果、http-data、logs、scripts 子目录），解释器用隔离 venv 里的 `python.exe`，不要用 PATH 上的系统 Python，也不要碰计划任务里的生产启动脚本。
- Mac Studio：若主脑决定在该机测量，需先建独立隔离树与私有样本/参考稿目录；不要在生产 clone 内就地测量。

## 更正（追加于 2026-10-06T03:16Z）

上方表格里有四处表述比证据能支撑的更强。以下逐条撤回其推论强度；表格其余单元格与本节冲突时以本节为准。

### 1. 「可信参考稿」应改为「存在；来源/标注可信性未核」

参考稿文件非空**只证明文件存在且有内容**，不证明它是可信的人工标注。上表三处「可信参考稿：存在，1 份非空」应读作「存在；来源/标注可信性未核」。可信性只能由独立证据（来源标注、人工复核记录、或与另一份独立标注的比对）支撑，本次三项均未做。

### 2. 三平台样本格式计数一致，不证明样本内容同一

上表显示三台机器各有 5 个 gold 文件 + 3 个匿名 WAV/MP4、格式计数相同。这只说明**格式齐备**，不说明这些文件是同一批素材、同一转写或同一来源。计数相同推不出集合相同。样本是否同源，只能由真实基线卡在同一轮的解码口径与参考稿比对里确认。

### 3. 模型目录大于 0 字节，不证明模型完整或能加载

上表的「模型缓存非空（约 544 MB）」只说明目录递归有字节。两个具体限制：

- **字节总量不是完整性判据。** 权重可能被截断、软链可能指向半成品，字节数照样非零。不得用 544 MB 当阈值。
- **可加载性从未被测。** 本次没有在任何一台机器上启动过引擎。

本轮为 Windows 补核了一次更窄的检查：按本仓 `config_server.py` 中 `ModelPaths` 硬编码的路径，逐个 `os.stat` / `os.path.exists` / `os.access(R_OK)` 检查 Paraformer 的 `model.onnx`、`tokens.txt` 与标点模型的 `model.onnx` 三个必需文件。结果：3/3 存在、3/3 可读、3/3 是常规文件、无缺失无不可读（用隔离 venv 的 Python 3.12.12 经 stdin 执行，Python 原语跟随 Windows reparse point，绕开了上轮 PowerShell 递归不跟随链接的问题）。

**这条结论的边界**：它只覆盖上述三个必需路径的存在与可读性，**不覆盖 ONNX 文件内容是否完整、不覆盖实际能否被 sherpa-onnx 加载、不覆盖加载后的识别质量**。三台机器的可加载状态一律待真实基线核。

另需说明：上轮报告里出现过的「Windows 与 Linux 读数 544 MB 一致」是**误写**。本轮之前 Windows 没有任何有效的字节读数（PowerShell 递归返回 0、补充探测无输出）；Windows 的模型状态当时是 unknown。任何 Windows 字节数字只能来自本轮这次文件级检查，而该检查刻意不输出字节数。

### 4. Mac Studio 只能写「候选根未找到，其他路径未知」

上表该行已按此改写。再次明确：那次探测只查了**一个**猜出来的准备根路径且未命中，没有做全盘搜索。不能写成「没有隔离树」「无样本」「皆无」。该机是否存在可用的 M7 隔离树与样本，目前是**未知**，不是「已确认没有」。

### 5. macOS 隔离机的 ffmpeg（已于 2026-10-06T03:26Z 补核，结论已变）

本轮获准 1 次 SSH 补核额度，一次成功。结果：该机**已安装 ffmpeg 8.1.2**（`ffmpeg -version` 返回码 0，版本首行已核），但**非交互 shell 的 PATH 不含其所在目录**，因此按裸 `ffmpeg` 调用会解析失败。

- 「PATH 查不到 ffmpeg」不等于未安装，本条 unknown **已闭合**。
- 实际二进制入口只存于本地私有回执，供后续卡复用，不写入本文档。
- 基线 CLI 以裸 `ffmpeg` 调用（`scripts/_baseline_http_ws.py` 里的 `["ffmpeg", ...]`），因此执行前必须让 PATH 包含该目录，否则解码计量会失败。这是执行时的环境要求，不是安装缺口。

### 6. SSH 调用次数（更正上轮自报）

上轮自报 9 次并称「与卡面偏差」，主脑指出 ≤6 是硬预算而非建议，且当时还有 1 次 Windows junction 补充探测未计入，实际**至少 10 次，超预算**。本轮记录：该超预算成立，不称无偏差。本轮获准 2 次追加额度并已全部用尽（1 次失败 + 1 次成功），不再追加。
